**Revised same-day (2026-08-13), after a prior-art research spike (`.lsa/research/rag-context-engine-and-repo-indexing-prior-art.md`) and owner review, before any epic build started:**
- **`project-map.yaml` = KEPT, not dropped.** The earlier gate decision to drop it entirely was reversed. No researched tool (Sourcegraph/Cody, SWE-agent, others) drops directory/keyword-level scoping in favor of embeddings alone — every one layers both. `project-map.yaml` stays as the coarse directory-level pre-filter; RAG ranks chunks within whatever scope it resolves. This also removes the single largest unapproved-scope-expansion flag the original roadmap row itself raised (`.lsa/roadmap.yaml:578`).
- **Sync mechanism = commit-triggered, not live.** The original design (a `PostToolUse` hook marking files dirty + a `SessionStart` hook reconciling) was found to have a real bug: with N concurrent sessions, no session's own edits get reconciled until *some* session starts fresh, so staleness is unbounded under exactly the parallel-agent-heavy usage this pitch is meant to serve. A redesign toward live per-edit reindexing was in progress when the owner paused it as needless complexity — real-time sync is how Cursor/Windsurf/Continue.dev do it, but only because they run a persistent background process inside an IDE; Claude Code has no equivalent (`rag-query.sh` is a one-shot CLI call, nothing runs between invocations), so copying that design was solving a problem we don't have while creating several new ones (branch switches, parallel worktrees/clones). The simpler, chosen design: only index **committed** code. A pre-commit hook rebuilds the index for the commit being made; a CI check backstops it in case the hook was skipped or bypassed. Uncommitted edits fall back to `Grep`/`Read`, same as today — this covers the large majority of search activity (the existing codebase) for a fraction of the engineering.

Why now: the owner's own reproduction of the DeepLearning.AI "AI Code Review" course pipeline completed 2026-08-10 with measured F1 gains on the course's sample corpus (diff-only 39.51% → context-aware 65.91% → ensemble 72.00%, `.lsa/roadmap.yaml:568`); the owner set numeric targets the same day and two downstream roadmap rows (`ai-code-review-skill`, `code-review-eval-harness`) are blocked on this item shipping first (`.lsa/roadmap.yaml:580`).

# RAG context engine — repo indexing and default-on retrieval across search-heavy skills

Build a local, commit-triggered repo index (chunk → embed → vector-store), packaged and run via Docker, as a second layer *inside* `project-map.yaml`'s existing directory scope — wired as the default (fallback-safe) search path for `lsa:discover`, `lsa:verify`, `lsa:reconcile`, and any other search-heavy skill or agent.

## Problem

Every LSA skill that needs to find something in the repo does it today with `Grep`/`Read` guided by two lightweight aids: the Read protocol (`lsa/knowledge/conventions.md:29-41`) and `project-map.yaml`, a directory-level "navigational atlas... not a file catalog" (`lsa/knowledge/conventions.md:37`). `project-map.yaml` narrows *which directory* to look in; nothing narrows *which paragraph or function inside it*. An agent still has to grep broadly and read whole files to confirm relevance within that directory. This scales linearly with repo size — 27 actor files across five plugins already (`.lsa/roadmap.yaml:558`).

The owner's own reproduction of the DeepLearning.AI "AI Code Review" course pipeline measured, on the course's sample corpus, that context-aware retrieval lifted F1 from 39.51% to 65.91%, and selective-context retrieval was the single largest jump in the whole pipeline (`.lsa/roadmap.yaml:568,580`). Those numbers are from the course corpus, not this repo — they motivate the bet, not a claim about this repo's own numbers yet.

**Definition of success:** the repo has a commit-triggered index that a search-heavy skill can query for a specific chunk within `project-map.yaml`'s resolved directory scope, with an observable fallback to `Grep`/`Read` when the index is unavailable, stale, or misses. **Not** in this definition: the owner's ≥50%/≥70% numeric targets — those are aspirational, unmeasured targets for the separate `code-review-eval-harness` roadmap row to grade; this pitch ships the mechanism, not the measurement.

## Appetite

**Big batch — a full cycle**, not a spike, but smaller than the original scope after the 2026-08-13 revision (no live-sync machinery, no `project-map.yaml` retirement). Explicitly outside the 2026-07-16 consolidation posture; the owner directed this as a new exception on 2026-08-10. Stated plainly, not re-litigated.

In appetite: initial + commit-triggered indexing, agent-invoked CLI retrieval, wiring RAG-within-`project-map`-scope into the three named consumers, Docker-based packaging.
Out of appetite: the eval harness itself, `ai-code-review-skill`, hosted/SaaS vector DB or embedding APIs, live/per-edit sync, dropping `project-map.yaml`.

## Solution sketch

- **Chunking:** structural, not fixed-token-window — Markdown chunks on H2/H3 boundaries (this repo already enforces fixed H2 headings on every `SKILL.md`/pitch, `manager/knowledge/pitch-structure.md:20-22`); bash scripts chunk by function/block; everything else falls back to a fixed-size overlapping window.
- **Embeddings:** local, CPU-only, no daemon — `[assumption, unverified this session]` something like `fastembed` (ONNX-based). Rejected: hosted API (network dependency + cost, works against "reliable on Pro-tier"); Ollama (needs a persistent background server).
- **Vector store:** `[assumption, unverified]` LanceDB — embedded, file-based, no separate server process beyond the container itself, native upsert/delete-by-key. Rejected: FAISS (no native delete-by-key); Chroma (heavier dependency surface outside embedded mode). Cache keyed at **chunk-content-hash granularity** (per `.lsa/research/rag-context-engine-and-repo-indexing-prior-art.md`, matching Cursor/Continue.dev practice) so one changed chunk in a large file doesn't force re-embedding the whole file on the next commit.
- **Packaging: Docker.** A `Dockerfile` packages the indexer/query scripts and their dependencies into a single image — this repo's first-ever containerization and first-ever runtime dependency of any kind. Host-side, `scripts/rag-index.sh` and `scripts/rag-query.sh` are thin wrappers that shell out to `docker run`, mounting the repo read-only and the index store read-write as local volumes. The index stays local-only — containerizing the *runtime*, not moving the *data* to a hosted service; No-go 3 still holds.
- **Sync mechanism (revised, simple):** a **pre-commit git hook** runs `scripts/rag-index.sh` to update the index for whatever changed in that commit (this repo has no existing git hooks — a new but standard, one-time setup step). A **CI check** alongside the existing `.github/workflows/lint.yml` verifies the index matches HEAD before merge, catching the case where the hook was skipped, never installed, or bypassed with `--no-verify`. No `PostToolUse`/`SessionStart` hooks, no live per-edit tracking, no worktree/branch cache-sharing engineering — each commit simply has its own index state, so branch switches and parallel worktrees/clones each just query whatever their current HEAD's index looks like.
- **Retrieval invocation:** an agent-invoked CLI, `scripts/rag-query.sh` — this repo's "deterministic work is scripted" convention (`.lsa/VISION.md` principle 10).
- **New artifacts:** `Dockerfile`, `scripts/rag-index.sh`, `scripts/rag-query.sh`, a gitignored local index volume (`.lsa/.rag-index/`), a `.git/hooks/pre-commit` script (with a documented one-time install step, since this repo has no existing hook-install mechanism), a CI check verifying index-matches-HEAD, and a new `gate: rag-index-fresh` check that also verifies the Docker daemon is reachable and fails loudly, not silently, if it isn't.
- **Modified artifacts:** `lsa/knowledge/conventions.md` Read protocol updated — `project-map.yaml` resolves the directory scope first (unchanged from today), then `rag-query.sh` ranks chunks within that scope, then `Grep`/`Read` tree-walk as the fallback. `lsa/skills/discover|verify|reconcile/SKILL.md` updated accordingly. `project-map.yaml` itself is **not** modified or removed.
- **Critical path:** a commit lands → pre-commit hook updates the index for the changed chunks (or CI catches a skipped hook before merge) → a skill resolves its directory scope via `project-map.yaml` exactly as today → within that scope, calls `rag-query.sh` → hit+fresh → uses retrieved chunks, skips whole-file reads → miss/stale/absent/daemon-down → falls back to `Grep`/`Read` exactly as today, zero regression, one-line notice.

## Rabbit holes

1. Retrieval-invocation mechanism as a platform capability (can `PreToolUse` actually inject context, or only allow/deny?) is unverified — ship the proven CLI path for v1, treat hook-injection as a confirmed-first fast-follow.
2. **New dependency + containerization footprint.** The repo currently ships zero Python/Node runtime dependency and zero containerization of any kind. Docker adds a real precondition — a running Docker daemon. Mitigation: the `gate:` check distinguishes "Docker unreachable" (an infrastructure fault, surfaced loudly) from an ordinary retrieval miss (silently falls back) — these must never be conflated.
3. `reconcile`'s independent-grader boundary (`lsa/skills/reconcile/SKILL.md:62,64`) — its RAG reads must pin to the exact graded sha; if the index is stale relative to that sha, `reconcile` falls back to `Grep`/`Read` for that call rather than trust a post-diff rebuilt index. Commit-triggered indexing makes this easier, not harder, than live sync would have — the index for a given sha is either fully built (from that commit's pre-commit run) or it isn't, no partial-dirty-state ambiguity.
4. **Pre-commit hook can be skipped or bypassed** (`git commit --no-verify`, or simply never installed on a fresh clone). Mitigation: the CI check is the actual guarantee, not the hook — the hook is a fast local convenience, the CI check is what makes staleness observable and blocking before merge.
5. Numeric targets treated as promises — mitigated by keeping Definition of Success mechanism-based, not F1/token-number-based.

## No-gos

1. No eval harness (separate roadmap row `code-review-eval-harness`).
2. No `ai-code-review-skill` or ensemble pipeline (separate, sequenced-after roadmap row).
3. No hosted/SaaS vector DB or embedding API — local-only. The Docker container runs on the owner's own machine; containerizing the runtime does not mean moving the data to a hosted service.
4. **This pitch DOES include Docker packaging** — a `Dockerfile` packaging the indexer/query scripts, run via thin host-side wrapper scripts. Chosen over a plain venv despite the added precondition (a running Docker daemon) and despite being this repo's first-ever containerization; owner's explicit call.
5. **This pitch does NOT drop `project-map.yaml`.** Reversed from the original 2026-08-10 gate decision after the 2026-08-13 prior-art research found no precedent for relying on embeddings alone — `project-map.yaml` stays as the directory-level pre-filter; RAG is the finer layer inside it.
6. This pitch does NOT run PR #85 (`rag-retrieve-before-read`) as a separate standalone phase first — supersedes/subsumes it; PR #85's technical locks (index key schema, local-only, no hosted SaaS) are inherited, not re-litigated.
7. This pitch does NOT build live/per-edit sync (`PostToolUse`/`SessionStart` reconciliation). That design was started and paused 2026-08-13 as unnecessary complexity for a CLI-invoked (not persistent-daemon) tool — see the revision note above.
