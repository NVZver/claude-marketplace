# Marketplace-as-MCP-server: a unified connection layer across MCP clients

Expose the same core/lsa/manager skill, knowledge, and agent content through a local MCP
server so any MCP-compatible client can use it, replacing today's per-client static ports.

## Problem

Whoever wants to use this marketplace's skills from a client other than Claude Code — Cursor,
VS Code, Antigravity IDE — currently gets a separately hand-built or LLM-regenerated copy of
the content, not a live connection to the source.

Evidence: `dist/cursor/` is explicitly "hand-maintained, no generator"
(scripts/opencode-dist-generate.sh:5). `dist/opencode/` is generated by driving `claude -p`
through a bespoke translation ruleset (scripts/opencode-dist-generate.sh:45-70) on a manual
regen-review-deploy cycle: "Review the diff in dist/opencode/ before deploying"
(scripts/opencode-dist-generate.sh:143-144). Both ports already have to special-case
Claude-Code-only mechanisms with no equivalent in the target client — hooks, ToolSearch,
deferred tools, TaskOutput, ScheduleWakeup, CronCreate, EnterPlanMode/ExitPlanMode
(scripts/opencode-dist-generate.sh:50-52) — with an explicit "do not invent a fake equivalent"
rule. A third client means a third bespoke translation ruleset, and every one drifts
independently the moment the source skill changes, since none of them is a live connection.

The coupling runs deeper than the packaging files: skill and agent bodies reference Claude
Code's own tool names directly in prose, not just in frontmatter — e.g.
`manager/agents/product-manager.md:4` declares `tools: Read, Grep, Glob`, and
`manager/skills/shape/SKILL.md:26` instructs "Invoke the `product-manager` agent via the
`Agent` tool." A server that just adds a wrapper file without touching this text would not
satisfy "no Claude-Code-specifics baked into the core mechanism."

Current workaround: maintain `dist/cursor/` by hand, and regenerate `dist/opencode/` via an
LLM translation script reviewed before deploy; the source of truth stays Claude-Code-native
(`.claude-plugin/plugin.json`, `hooks.json`, `${CLAUDE_PLUGIN_ROOT}`), and every other client
gets a lossy, manually-reviewed derivative.

Definition of success: an MCP client other than Claude Code can call the marketplace's skills
as tools and read its knowledge files as resources against one running local server, with zero
per-client static copies to hand-maintain or regenerate — a change to a skill's Markdown body
is live for every connected client without a translation/regen/deploy step.

## Appetite

Big batch — this is a multi-epic architectural change; `manager:decompose` will slice it into
a build sequence. First-slice boundary (confirmed above): `core` + `lsa` + `manager` only —
the same three plugins the existing `dist/opencode` port already covers
(scripts/opencode-dist-generate.sh:129-140) — with `prompt-engineer` and `observer` as a
follow-up slice, and the RAG/vector-search subsystem (`lsa/skills/bootstrap-rag`, `lsa/docker/`,
`*rag*` scripts) excluded, mirroring the exclusion already made for `dist/opencode`
(scripts/opencode-dist-generate.sh:18-19). Out of appetite for this pitch: a hosted/remote
server variant (see No-gos).

## Solution sketch

- **Key user interactions:** a developer configures their MCP-compatible client (Cursor,
  VS Code, Antigravity, and Claude Code itself as an additional path — see gate decisions)
  to launch the marketplace's MCP server via stdio once; from then on that client calls the
  exposed skills as tools and reads exposed knowledge files as resources, with no per-client
  copy step. Claude Code's existing native plugin install path (`.claude-plugin/plugin.json`,
  `hooks.json`) is kept unchanged alongside this.
- **Main components:** (1) a new stdio MCP server entry point that reads the existing `core/`,
  `lsa/`, `manager/` Markdown tree at startup and registers each skill/agent/knowledge file as
  an MCP primitive, with no duplicated content; (2) a rephrasing pass over skill/agent Steps
  sections that name Claude Code tools directly (`Read`, `Grep`, `Glob`, `Write`, `Agent`,
  `Skill`, `AskUserQuestion`), generalizing the wording per the user's own carve-out — content
  and meaning unchanged, tool-name references neutralized; (3) agents (`product-manager`,
  `project-manager`) exposed as prompt/content primitives that the connecting client's own
  agent loop runs — the server itself never spawns a sub-agent conversation or makes its own
  LLM calls; (4) a documented, explicit gap list for mechanisms with no MCP equivalent
  (hooks, `ToolSearch`, deferred tools, `TaskOutput`, `ScheduleWakeup`, `CronCreate`,
  `EnterPlanMode`/`ExitPlanMode`), reusing the "drop, or note briefly as unavailable — do not
  invent a fake equivalent" policy already proven in `scripts/opencode-dist-generate.sh:50-52`;
  (5) retirement of `dist/cursor/` and `dist/opencode/` once the live server covers the clients
  they targeted; (6) a `SECURITY.md` update reflecting the new local-server trust boundary.
- **Critical path:** server starts (spawned by a connecting client's own MCP config) → reads
  the first-slice skill/knowledge tree → registers each skill as a callable tool and each
  knowledge file as a resource → a connecting client calls a tool → the server returns the
  skill's instruction content unchanged → the connecting client's own model executes the
  instructions.

## Rabbit holes

1. Claude-Code-only mechanisms with no confirmed MCP equivalent (`AskUserQuestion`, `ToolSearch`,
   deferred tools, `TaskOutput`, `ScheduleWakeup`, `CronCreate`, `EnterPlanMode`/`ExitPlanMode`,
   the one `SessionStart` hook — SECURITY.md:5 "Markdown instruction files plus one shell hook")
   — risk of inventing a fake substitute, which breaks `core/ground-rules` Rule 2 (no fake
   confidence). Mitigation: reuse the explicit drop/note-as-unavailable policy already proven
   at `scripts/opencode-dist-generate.sh:50-52` rather than designing new fake equivalents.
2. Tool-name coupling is inside instruction prose, not just frontmatter (see Problem section,
   `manager/agents/product-manager.md:4`, `manager/skills/shape/SKILL.md:26`) — a shallow
   "just stand up a server" pass will not satisfy the stated requirement. Mitigation: the
   rephrasing pass in the Solution sketch is scoped as its own tracked piece of work, not an
   afterthought.
3. Security posture claim goes stale the moment a server exists: SECURITY.md:3-4 currently
   states "There is no server, no hosted service" as the entire trust-boundary claim. Standing
   up any MCP server — even local-only, stdio-spawned — makes that sentence false the day this
   ships. Mitigation: a SECURITY.md update is part of this pitch's build, not a follow-up.
4. Three divergent distribution mechanisms mid-migration if `dist/cursor/` and `dist/opencode/`
   are left running unchanged alongside a new live server — drift risk goes up, not down, until
   the retirement decision (confirmed above: additive, ports retire) is executed.

## No-gos

1. This pitch does NOT cover a hosted or network-exposed MCP server — local, stdio-spawned per
   the confirmed transport gate; a remote/multi-user variant is a separate pitch requiring its
   own security review, since it would break the "no server, no hosted service, no secrets, no
   PII" trust boundary claim at SECURITY.md:3-4 in a materially different way than a local-only
   server does.
2. This pitch does NOT cover the RAG/vector-search infrastructure (`lsa/skills/bootstrap-rag`,
   `lsa/docker/`, `*rag*` scripts) — excluded for the same reason it's excluded from
   `dist/opencode` today (scripts/opencode-dist-generate.sh:18-19): a separate, heavier subsystem.
3. This pitch does NOT rewrite the substance of the eight ground rules, the output rules, or the
   pitch-structure content — only the connection/packaging mechanism and in-prose tool-name
   references change, per the user's own instruction that "the skill/knowledge content itself
   stays the same."
4. This pitch does NOT pick the MCP SDK, language, or runtime that implements the server — that
   is an implementation-detail decision for `lsa:specify`/`lsa:delegate`, not a shaping-level call.
5. This pitch does NOT have the MCP server spawn or manage sub-agent conversations server-side
   (confirmed gate: agents expose as prompt/content, not server-side execution) — that would
   require the server to hold model credentials and make its own LLM calls, a materially bigger
   and different kind of system.
6. This pitch does NOT retire Claude Code's native plugin install path (`.claude-plugin/plugin.json`,
   `hooks.json`, the documented `/plugin install` flow, README.md:61-69) — confirmed additive:
   Claude Code keeps its native path and its one `SessionStart` hook; the MCP server is the
   connection layer for other clients.
